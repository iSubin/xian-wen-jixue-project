# 用户级采集账号设计

本文记录 XianWen 后续面向多用户、线上服务时的采集账号方案。目标是把当前「全局 B 站 SESSDATA」扩展为「每个用户维护自己的站点凭据」，并为 B 站、小鹅通、投研大师以及后续更多站点提供统一的接入模型。

本文是产品与技术设计文档，并记录当前已经落地的 MVP 范围。

---

## 1. 背景

当前项目已经具备以下能力：

- B 站视频采集：支持字幕优先、`SESSDATA`、临时 Netscape cookiefile、`yt-dlp` 下载、ASR 回退。
- 小鹅通视频采集：支持从登录态 Cookie 解析 HLS 地址，再进入现有下载、转录、总结链路。
- 投研大师视频采集：支持从登录态信息解析真实媒体地址。
- 转录设置：已有全局 B 站 `SESSDATA` 配置。

这些能力在个人本地使用时可行，但如果后续上线服务 C 端用户，不能继续依赖一个全局 B 站账号或全局 Cookie。更合理的方向是：

> 每个用户维护自己可访问站点的采集凭据，任务执行时只使用任务所属用户的凭据。

---

## 2. 设计结论

推荐方案：

1. 在「转录设置」中新增「采集账号」模块。
2. 将当前全局 B 站 SESSDATA 改造为「系统兜底账号」，不作为用户默认授权。
3. 每个用户可以为不同站点维护自己的凭据。
4. 服务端按用户隔离凭据，任务只能使用当前用户自己的站点凭据。
5. 凭据按敏感密钥处理：加密存储、不可回显、可验证、可删除、日志脱敏。
6. 当前 MVP 已将「从浏览器获取」作为主流程：用户在本机浏览器登录后点击按钮，系统自动读取对应站点登录态并保存。
7. 手动粘贴 Cookie 只作为高级兜底入口，默认隐藏在「高级：手动填写」中。
8. 后续可以接入 Chrome 插件，让线上服务也能在用户授权下从用户浏览器向云端同步凭据。

不推荐方案：

- 不推荐所有用户共享同一个全局 B 站 SESSDATA。
- 不推荐让用户填写 B 站账号密码、小鹅通账号密码或验证码。
- 不推荐把 Cookie 当作普通配置明文写入 `settings.json`。
- 不推荐在日志、任务 payload、导出内容中保留完整 Cookie 或签名 URL。

## 3. 产品形态

短期可以放在「转录设置」里，作为一个新的区块：

```text
转录设置
  - 模型设置
  - B 站字幕优先
  - 采集账号
      - 哔哩哔哩
      - 小鹅通
      - 投研大师
      - 后续更多站点
```

长期可以独立为「账号连接」或「站点凭据」页面。

### 3.1 站点卡片

每个已支持站点展示一张卡片：

```text
哔哩哔哩
状态：已连接 / 未连接 / 已失效
凭据类型：SESSDATA
当前账号：昵称或 UID
最后验证：2026-05-31 15:20
最近使用：任务名称或任务 ID
主操作：从浏览器获取
次要操作：删除已保存账号
高级：手动填写 SESSDATA 并保存
```

```text
小鹅通
状态：已连接 / 未连接 / 已失效
凭据类型：Cookie Header
适用域名：*.h5.xiaoeknow.com
最后验证：-
主操作：填写视频链接或店铺域名后，从浏览器获取
次要操作：删除已保存账号
高级：手动填写 Cookie Header 并保存
```

```text
投研大师
状态：已连接 / 未连接 / 已失效
凭据类型：web_qtstr
最后验证：-
主操作：从浏览器获取
次要操作：删除已保存账号
高级：手动填写 web_qtstr 并保存
```

### 3.2 凭据展示规则

完整凭据不得回显。

允许展示脱敏摘要：

```text
SESSDATA=abcd****wxyz
Cookie=xe_session=ab****yz; other_cookie=<redacted>
web_qtstr=ab****yz
```

用户只能：

- 新增
- 更新
- 验证
- 删除

不能查看完整明文。

正常用户不需要自己寻找 Cookie。默认路径是：先在浏览器登录目标站点，再点击「从浏览器获取」。手动粘贴只保留给排障、开发和无法自动读取浏览器登录态的场景。

### 3.3 用户提示文案

需要明确告诉用户：

- 这些凭据只用于处理用户自己有权访问的内容。
- 用户可以随时删除已保存凭据。
- 系统不会展示完整凭据。
- 如果凭据失效，任务会提示用户重新连接对应站点。
- 不支持绕过 DRM、付费限制、平台风控或用户无权访问的内容。

## 4. 支持站点与凭据类型

### 4.1 哔哩哔哩

Provider ID:

```text
bilibili
```

推荐凭据类型：

```text
credential_type = sessdata_bundle
```

MVP 可以先支持：

```json
{
  "SESSDATA": "<user-sessdata>"
}
```

更稳的结构：

```json
{
  "SESSDATA": "<user-sessdata>",
  "DedeUserID": "<user-id>",
  "bili_jct": "<csrf-token>"
}
```

使用要求：

- 优先使用 B 站公开字幕。
- 需要登录态时，使用当前用户自己的 B 站凭据。
- 下载时仍优先生成临时 Netscape cookiefile，任务结束后删除。
- 现有全局 SESSDATA 只能作为系统兜底，不应覆盖用户自有凭据。

### 4.2 小鹅通

Provider ID:

```text
xiaoetong
```

推荐凭据类型：

```text
credential_type = cookie_header
```

示例结构：

```json
{
  "host_scope": "appexpqpqic7617.h5.xiaoeknow.com",
  "cookie_header": "<cookie-header>"
}
```

使用要求：

- 针对普通学员访问，使用 Cookie Header 解析课程视频 HLS。
- 针对商户或企业客户，后续应优先支持官方 API token / access_token。
- 同一用户可能拥有多个小鹅通店铺域名，应允许保存多个 host scope。

### 4.3 投研大师 / Homeway

Provider ID:

```text
homeway
```

推荐凭据类型：

```text
credential_type = web_qtstr
```

示例结构：

```json
{
  "web_qtstr": "<web-qtstr>"
}
```

使用要求：

- 用于解析投研大师图文视频页对应的真实媒体地址。
- `web_qtstr` 只能按当前用户隔离使用。
- 解析出的媒体 URL、token、sign 等必须脱敏记录。

### 4.4 后续站点

新增站点必须先定义 Provider Adapter，不允许在 worker 中散落站点特化逻辑。

每个 Provider 至少声明：

```text
provider_id
display_name
supported_url_patterns
credential_schema
validate_credential()
resolve_media()
redact_secret()
```

## 5. 后端数据模型

### 5.1 User

线上版本需要用户体系。最小字段：

```text
id
email / phone / oauth_id
display_name
created_at
updated_at
```

### 5.2 ConnectedAccount

保存用户与站点的连接关系，不直接保存明文凭据。

```text
id
user_id
provider
display_name
credential_type
secret_ref
domain_scope
status
last_verified_at
last_used_at
last_error
created_at
updated_at
```

字段说明：

- `provider`：`bilibili`、`xiaoetong`、`homeway` 等。
- `credential_type`：`sessdata_bundle`、`cookie_header`、`web_qtstr`、`official_api` 等。
- `secret_ref`：指向加密密钥存储，不保存明文。
- `domain_scope`：用于限制该凭据只作用于指定站点或店铺域名。
- `status`：`connected`、`expired`、`revoked`、`needs_reauth`。

### 5.3 CredentialSecret

保存加密后的凭据。

```text
id
encrypted_payload
key_version
created_at
updated_at
```

要求：

- 数据库只保存密文。
- 解密密钥不与数据库放在一起。
- 支持 key version，方便未来轮换密钥。
- 读取凭据必须有用户、任务和 Provider 上下文。

### 5.4 CredentialUseLog

记录凭据使用情况，便于审计和问题排查。

```text
id
user_id
connected_account_id
provider
task_id
action
result
error_code
created_at
```

注意：

- 不记录明文 Cookie。
- 不记录完整媒体签名 URL。
- 只记录脱敏后的错误信息和行为类型。

## 6. 任务执行流程

### 6.1 普通在线视频任务

```text
用户提交视频链接
  -> 系统识别 provider
  -> 查询当前用户是否有该 provider 的可用 ConnectedAccount
  -> 构造任务 payload
  -> worker 使用该用户凭据解析媒体
  -> 下载 / 转录 / 抽帧 / 总结
  -> 更新任务结果
```

### 6.2 凭据选择优先级

推荐优先级：

1. 任务明确指定的用户连接账号。
2. 当前用户该 provider 的默认连接账号。
3. 无 Cookie / 无凭据公开采集。
4. 系统级兜底账号。

系统级兜底账号只允许用于公开视频或公开字幕场景，不应用于用户私有内容。

### 6.3 凭据失效流程

当 worker 遇到 401、403、登录过期、验证码、风控等错误：

```text
标记 ConnectedAccount.status = needs_reauth
记录 last_error
任务状态进入 FAILED 或 WAITING_FOR_CREDENTIAL
前端提示用户更新对应站点凭据
```

不应自动重试大量请求，也不应尝试绕过平台风控。

## 7. Provider Adapter 设计

为避免后续每接一个网站都改 worker，建议新增统一接口：

```text
ProviderAdapter
  can_handle(url) -> bool
  required_credential_type(url) -> str | None
  validate_credential(credential) -> ValidationResult
  resolve_media(url, credential) -> ResolvedMedia
  redact(value) -> str
```

ResolvedMedia 建议结构：

```text
source_url
media_url
title
duration
quality
headers
expires_at
metadata
```

现有站点应逐步迁移：

- BilibiliAdapter
- XiaoetongAdapter
- HomewayAdapter

worker 不直接知道每个网站的 Cookie 细节，只接收 `ResolvedMedia` 或标准错误。

## 8. 安全要求

这是该方案能否上线的关键。

### 8.1 存储安全

- 凭据必须加密存储。
- 不允许明文写入 `config/settings.json`。
- 不允许在任务 payload 中持久化完整 Cookie。
- 解密只发生在 worker 处理当前任务的短时间内。
- 临时 cookiefile 必须权限最小化，任务结束后删除。

### 8.2 访问控制

- 用户只能管理自己的 ConnectedAccount。
- worker 只能读取任务所属用户的凭据。
- 管理员后台默认不显示用户凭据明文。
- API 必须校验用户身份与资源归属。

### 8.3 日志脱敏

必须脱敏：

- `SESSDATA`
- `Cookie`
- `token`
- `access_token`
- `sign`
- `web_qtstr`
- `t`
- `us`
- HLS / DASH URL 中的敏感 query 参数

错误信息写入任务前也必须脱敏。

### 8.4 删除与撤销

用户必须可以删除站点凭据。

删除后：

- `ConnectedAccount.status = revoked`
- 删除或不可逆销毁 `CredentialSecret`
- 未开始任务不再使用该凭据
- 已运行任务不再重试该凭据

### 8.5 合规边界

产品表达应是：

> 帮助用户整理自己有权访问的学习内容。

不应表达为：

> 下载器、破解、绕过会员、绕过付费、绕过 DRM、代登录。

---

## 9. 与当前全局 SESSDATA 的关系

当前全局 B 站 SESSDATA 不应直接删除，但需要降级定位：

```text
系统级 B 站登录态
仅用于公开内容兜底，不作为用户授权。
```

迁移建议：

1. 保留全局配置，但前端文案改为「系统兜底账号」。
2. 新增用户级 B 站连接账号。
3. 任务提交时优先使用用户级凭据。
4. 全局 SESSDATA 只在用户未配置凭据且内容可公开访问时尝试。
5. 后续线上多用户版本可以关闭全局 SESSDATA 或仅管理员可配置。

## 10. API 设计草案

### 10.1 获取支持站点

```text
GET /providers
```

返回：

```json
[
  {
    "id": "bilibili",
    "name": "哔哩哔哩",
    "credential_types": ["sessdata_bundle"],
    "supports_validate": true
  }
]
```

### 10.2 获取当前用户连接账号

```text
GET /connected-accounts
```

返回脱敏信息，不返回明文凭据。

### 10.3 新增或更新连接账号

```text
PUT /connected-accounts/{provider}
```

请求体：

```json
{
  "credential_type": "sessdata_bundle",
  "payload": {
    "SESSDATA": "<user-sessdata>"
  }
}
```

服务端保存前：

- 校验 provider。
- 清洗换行和非法字符。
- 加密 payload。
- 可选执行一次 validate。

该接口主要作为高级手动填写、调试和后续管理后台入口；普通用户的主路径是从浏览器导入。

### 10.4 从浏览器导入连接账号

```text
POST /connected-accounts/{provider}/from-browser
```

用途：

- B 站：从本机浏览器读取 `SESSDATA`。
- 小鹅通：根据 `source_url` 或 `domain_scope` 定位店铺域名，再读取该域名 Cookie Header。
- 投研大师：从本机浏览器读取 `web_qtstr`。

请求体：

```json
{
  "source_url": "https://appexpqpqic7617.h5.xiaoeknow.com/p/course/video/...",
  "domain_scope": "appexpqpqic7617.h5.xiaoeknow.com",
  "display_name": "小鹅通 appexpqpqic7617"
}
```

响应只返回脱敏账号视图，不返回明文凭据。

### 10.5 验证连接账号

```text
POST /connected-accounts/{id}/validate
```

返回：

```json
{
  "status": "connected",
  "display_name": "用户昵称或 UID",
  "last_verified_at": "2026-05-31T15:20:00+08:00"
}
```

当前 MVP 尚未实现独立 validate 接口；浏览器导入只证明本机浏览器中存在对应登录态，不等价于远端业务接口一定可用。

### 10.6 删除连接账号

```text
DELETE /connected-accounts/{id}
```

删除后不可恢复明文凭据。

## 11. 前端要求

### 11.1 设置页

新增「采集账号」区块。

每个站点需要显示：

- 站点名称
- 当前状态
- 凭据类型
- 脱敏摘要
- 主按钮「从浏览器获取」
- 已保存账号的弱化删除按钮
- 小鹅通的视频链接或店铺域名输入框
- 折叠的「高级：手动填写」入口

手动凭据输入和「保存手动凭据」按钮默认必须收起，避免普通用户误以为必须自己寻找 Cookie。

### 11.2 任务提交

提交链接后，前端可根据 URL 初步识别站点：

- 如果该站点需要凭据但用户未配置，提示用户先连接账号。
- 如果该站点凭据已失效，提示更新。
- 如果是公开内容，允许继续无凭据提交。

### 11.3 错误提示

错误提示要面向用户：

```text
你的哔哩哔哩登录态已失效，请在转录设置 - 采集账号中更新。
```

不要展示：

```text
HTTP 403 SESSDATA invalid <redacted>
```

## 12. 后端实现阶段

### 当前 MVP 状态（2026-05-31）

已落地：

- 新增 `connected_accounts` 与 `credential_secrets` 两张表。
- 支持 SQLite 与 PostgreSQL，两者走同一套 SQLAlchemy 模型。
- 新增 Docker Postgre 开发实例：`docker compose -f docker-compose.postgres.yml up -d postgres`。
- 支持 `XIANWEN_DATABASE_URL` 或 `config.database.url` 指定数据库连接。
- 凭据 payload 使用 AES-GCM 加密后存储，API 只返回脱敏摘要。
- 新增 `GET /providers`、`GET /connected-accounts`、`PUT /connected-accounts/{provider}`、`DELETE /connected-accounts/{id}`。
- 当前本地单用户模式使用 `local-user`；后续接入用户体系后由认证中间件提供真实 `user_id`。
- B 站、小鹅通、投研大师任务提交时会按当前用户读取对应凭据，并注入 worker 的运行时 payload。
- 前端「转录设置」已新增「采集账号」区块，主设置弹窗与侧边栏快捷设置保持一致。
- 采集账号支持从本机浏览器导入登录态：B 站读取 `SESSDATA`，小鹅通按视频链接或店铺域名读取 Cookie Header，投研大师读取 `web_qtstr`。
- 前端主流程已收敛为「从浏览器获取」，手动粘贴 Cookie 收到「高级：手动填写」。
- 新增轻量 UI 回归检查：`npm run test:accounts-ui`。

尚未落地：

- 独立用户注册 / 登录 / Session。
- 凭据在线验证接口（当前导入只证明浏览器中有登录态，不做远端有效性验证）。
- 凭据使用审计日志。
- 凭据失效时自动标记 `needs_reauth`。
- Provider Adapter 完整抽象。
- Chrome 插件导入凭据。

### 阶段 1：用户级 B 站凭据

目标：

- 新增 ConnectedAccount / CredentialSecret。
- 支持当前用户保存 B 站 SESSDATA。
- worker 从任务所属用户读取 B 站凭据。
- 保持现有全局 SESSDATA 兜底。
- 日志与错误信息完成脱敏。

验收：

- 用户 A 的任务不能使用用户 B 的 SESSDATA。
- 删除用户 A 的 B 站凭据后，用户 A 的私有 B 站任务会提示重新连接。
- 公开视频仍可无凭据处理。
- 临时 cookiefile 会被删除。

### 阶段 2：小鹅通凭据接入

目标：

- 小鹅通 resolver 支持从 ConnectedAccount 获取 Cookie Header。
- 支持多个小鹅通 host scope。
- 解析失败时标记该用户的小鹅通凭据失效。

验收：

- 同一用户可以维护多个小鹅通店铺凭据。
- 用户之间凭据完全隔离。
- HLS URL 日志脱敏。

### 阶段 3：投研大师凭据接入

目标：

- Homeway resolver 支持用户级 `web_qtstr`。
- 取消对本机 Chrome Cookie 的线上依赖。

验收：

- 用户维护自己的投研大师凭据后可采集对应内容。
- 无凭据时给出清晰提示。

### 阶段 4：Provider Adapter 收敛

目标：

- 抽象 ProviderAdapter。
- 将 B 站、小鹅通、投研大师迁移到统一接口。
- worker 只依赖标准 ResolvedMedia。

验收：

- 新增站点不需要改核心 worker 主流程。
- 每个 Provider 都有独立测试。

### 阶段 5：Chrome 插件导入

目标：

- 插件读取用户当前浏览器登录态。
- 用户授权后由插件把必要站点凭据发送到云端 API。
- 云端服务不直接读取用户本机 Cookie，只接收用户授权传递的最小凭据。
- 减少手工复制 Cookie，并为线上 C 端用户提供可用的账号连接路径。

验收：

- 插件只请求必要站点权限。
- 插件不读取无关域名 Cookie。
- 用户可以明确知道本次连接的是哪个站点。

## 14. 运营与产品边界

上线时需要在用户协议或功能说明中明确：

- 用户只能采集自己有权访问的内容。
- 用户自行负责第三方账号的授权和合规使用。
- 平台不支持绕过付费、会员、DRM 或访问控制。
- 凭据失效、平台风控、接口变化可能导致任务失败。
- 用户可以随时删除已保存凭据。

产品命名建议：

- 使用「采集账号」「连接账号」「站点凭据」。
- 避免使用「破解」「下载会员视频」「绕过限制」等表达。

## 15. 待确认问题

后续实现前需要确认：

1. 多用户体系先采用本地账号密码、手机号登录，还是第三方 OAuth。
2. MVP 是否继续使用 SQLite，还是直接切换到线上数据库。
3. 凭据加密使用应用主密钥、云 KMS，还是先使用部署环境密钥。
4. 是否需要管理员后台查看凭据状态统计。
5. Chrome 插件是否纳入第一阶段，还是等 B 站用户级凭据稳定后再做。

## 16. 一句话总结

当前最合适的演进方向是：

> 将「全局 SESSDATA」升级为「用户级采集账号系统」，在转录设置中列出已支持网站，让每个用户维护自己可访问站点的凭据；后端按用户隔离、加密保存、按任务取用，并通过 Provider Adapter 支持更多站点。
